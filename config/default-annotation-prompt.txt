## 任务目标

请依据可核验的业务资料，为当前表生成一版完整、可供人工审核的本体标注草稿。

标注的重点是解释这张表及其字段在业务上代表什么、承担什么职责、与哪些业务对象有关。不要复述数据库名称，也不要在描述中介绍代码实现、SQL、接口调用或程序流程。

草稿必须包含：

- 类名、类描述和类别名
- 所有原始字段对应的本体属性名、详细描述和字段别名
- 有充分证据支持的枚举引用及完整枚举定义
- 每个字段的分析摘要和证据来源
- 无法确认时需要人工处理的待澄清事项

所有类描述、类别名、字段描述和字段别名都必须填写，不得用空字符串或空 aliases 数组占位。

`isLocalId`、`isCode`、`isDisplayName`、`isSemantic` 均由人工标注。Claude 不得判断、新增或修改这些值；如果 `current-draft.json` 已经包含人工设置，则原样保留，否则保持系统默认值。

## 资料的用途

### 业务语义证据

以下资料用于判断当前表和字段的实际业务含义，按优先顺序使用：

1. `input-table.json` 中的表描述、字段 `description`、字段 `remark`、主键、外键和原始取值说明。
2. `dataset-context.json` 与关系索引中的直接父表、子表、外键方向和字段映射。
3. RB、WEB、DB 目录中的代码、SQL、配置、常量、校验条件、固定赋值和使用上下文。
4. 当前 0 级域中与本表存在直接业务关系的其他表。
5. 与当前业务对象一致，并且能够被其他资料印证的既有 Ontology 标注。

### 格式参考

`Teleco_Context` 只用于了解：

- Ontology JSON 的结构
- 中英文描述应达到的详细程度
- aliases 的数量和表达方式
- `enum_ref` 与枚举文件的组织格式

每个任务最多读取 `Teleco_Context` 中一个有代表性的 entity-class 文件。需要确认枚举输出结构时，可以额外读取一个 enum 文件。

不得在 `Teleco_Context` 中反复搜索当前表名或全部字段名，不得批量遍历其中的 entity-classes 和 enums，也不能把其他业务对象的名称、描述、别名或枚举值套用到当前表。

`Teleco_Context` 只能回答“标注结果应该怎样表达”，不能作为当前表业务含义的证据。

## 检索流程

1. 完整读取当前工作目录中的：

   - `input-table.json`
   - `dataset-context.json`
   - `current-draft.json`（如果存在）

2. 分析当前表的原始信息：

   - 表描述对应什么业务对象
   - 主键标识什么实体
   - `foreignKeys` 表明当前表依赖哪些父表
   - `referencedBy` 表明哪些子表依赖当前表
   - 字段描述和备注提供了哪些业务事实、取值及约束

3. 在 RB、WEB、DB 中精确搜索当前 `tableName`。

   阅读命中的表定义、SQL、配置、对象映射和直接使用上下文，建立表级业务理解。

4. 逐个搜索当前表的字段名，并重点阅读字段附近的：

   - 赋值来源
   - 校验条件
   - 常量定义
   - 条件分支
   - 字典或配置项
   - 关联查询
   - 业务注释

   这些内容用于确认字段表达的业务事实、关联对象、取值范围及适用边界。

5. 精确名称没有结果时，才搜索有资料依据的完整名称、去前缀名称或同义词。不要先进行宽泛的概念搜索。

6. 仅在核对外键关系、业务边界或统一命名确有必要时读取同域其他表，不要遍历整个域。

7. 完成业务证据检索后，读取一个 `Teleco_Context` entity-class 样例校准格式和描述粒度，然后停止在该目录继续查找。

8. 已有证据能够支持结论时，应结束相关检索，避免围绕相同关键词或目录重复搜索。

## 类标注要求

### className

使用完整、自然、通用的英文 PascalCase 业务概念。

优先复用当前业务资料中已经明确存在的本体类名。不要直接使用 `ACCT`、`PNT`、`INST` 等数据库缩写。例如资料明确表达“账户”时，应使用 `Account`，而不是 `Acct`。

### classDescription

必须提供含义等价、信息范围一致的中英文业务描述，格式如下：

中文描述：说明该实体是什么、代表哪个业务对象、承担哪些业务职责、与关键上下游对象的关系，以及适用边界。

English Description: Provide an equivalent English business-semantic description with the same scope and level of detail.

描述应形成完整段落，不能只写“用于记录……”的一句话。

### classAliases

提供 4–12 个有意义且不重复的中英文别名，覆盖：

- 正式业务名称
- 常用业务称呼
- 有证据支持的同义词

不得通过改变 `tableName` 或 `className` 的大小写来凑数，也不能从格式样例复制无关别名。

## 字段标注要求

### entityColumn

使用英文 camelCase，类内属性名必须唯一。

名称应表达字段的实际业务含义。当前业务域已有一致命名，并且能够被资料确认时，优先复用该命名。

### detailedDescription

每个字段都必须提供含义等价的中英文详细描述：

中文描述：说明字段表达的业务事实、所属对象、作用范围、与其他业务概念的关系，以及资料能够证明的业务限制。

English Description: Provide an equivalent English business-semantic description with the same scope and level of detail.

不得描述数据库类型、字段读写、SQL 查询、序列器、接口或程序执行过程。

### aliases

每个字段提供 2–8 个不重复的别名，至少包含：

- 一个自然英文名称
- 一个中文业务名称

只有存在可靠依据时才能增加业务全称、常用称呼或同义词，不得扩展未经证实的业务含义。

### included 与数据类型

`included` 表示字段是否进入 Ontology 和 RDB Mapping。

只能处理 `input-table.json` 中存在的字段，不能创造数据库列。字段的数据类型由 Schema Atlas 根据原始数据库类型转换，Claude 不负责修改。

### 人工标志

以下字段只允许人工设置：

- `isLocalId`
- `isCode`
- `isDisplayName`
- `isSemantic`

处理规则：

- 不根据字段名、主键、外键或代码自行判断
- 不提出推荐值
- 不修改已有人工设置
- 没有人工设置时保持默认状态

## 枚举识别

是否属于枚举，只能根据原始 JSON 和当前业务代码中的实际证据判断，不能通过字段名称、前缀或后缀推测。

按以下顺序检查：

1. 字段 `description` 或 `remark` 是否明确列出有限取值及各取值的含义。
2. RB、WEB、DB 中是否存在与该字段直接相关的常量集合、字典配置、固定赋值、校验规则或条件分支。
3. 当前业务域已有 Ontology 中是否存在语义和取值均一致的 `enum_ref` 及枚举文件。

只有能够确认有限取值集合及其业务含义时，才能设置 `enumRef`。

外键标识、自由文本、普通业务编码以及没有有限取值证据的字段不得标记为枚举。

确认枚举后：

- 优先复用当前业务域中语义和取值一致的 `enum_name`
- 没有可复用名称时，使用 `entityColumn` 首字母大写后的名称，例如 `accountClass` 对应 `AccountClass`
- `enumDescription` 必须包含完整的中英文业务说明
- `enumValues` 至少包含一项
- 每个枚举值的 `value`、`aliases` 和 `description` 都必须填写
- `description` 使用一个同时包含中文和等价英文含义的字符串
- 不得创建 `description_en` 或 `descriptionEn`
- 实体属性只保留 `enum_ref`，完整枚举定义单独导出

如果资料只能证明该字段可能存在固定取值，但无法确认完整取值集合或各值含义，则加入待澄清，不得生成不完整枚举。

## 字段分析与证据

每个字段必须填写 `analysisSummary`，使用 3–6 句中文说明：

- 对字段业务含义的理解
- `entityColumn` 的命名依据
- aliases 的选择依据
- 字段是否具有外键语义
- 是否发现枚举证据
- 当前存在的不确定性

不要在分析中替人工判断 `isLocalId`、`isCode`、`isDisplayName` 或 `isSemantic`。

`reason` 只填写能够回查的具体证据，例如：

- 文件路径
- 表名或字段名的命中位置
- 相关常量或配置
- 外键字段映射
- 原始 `remark` 中的取值说明

如果提到 `Teleco_Context`，只能将其标记为格式参考，不能用它证明当前字段的业务含义。

## 待澄清事项

只有完成以下检查后仍然无法确认，才可以创建 `todos`：

- 当前表描述和字段备注
- 直接关联表及关系索引
- 必要的同域表
- `current-draft.json`
- RB、WEB、DB 中的精确表名和字段名
- 已配置的其他业务参考路径

每条 todo 必须包含：

- 需要人工确认的问题
- `checkedSources`：实际检查过的文件或线索
- `reason`：缺少什么证据，或者哪些资料存在冲突
- 能够提出的候选答案

存在待澄清事项时，仍需根据已经确认的证据生成可审核草稿，不得将必填名称、描述或 aliases 留空。

## 最终输出

`reply` 使用简洁中文汇总：

- 已完成的标注
- 使用的主要业务证据
- 已确认的枚举
- 需要人工处理的问题

最终结果必须严格符合指定 JSON Schema。
