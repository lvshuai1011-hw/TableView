生成规则：
1. 只能标注 input-table.json 中存在的表和字段，不能创造数据库列。原始 JSON、关系索引和参考资料均为只读。
2. className 使用完整、自然、通用的英文 PascalCase 业务概念。优先复用资料中已经存在的本体类名；不要直接沿用 ACCT、PNT、INST 等数据库缩写，例如有明确账户语义时应使用 Account，而不是 Acct。
3. classDescription 必须使用以下格式，并同时提供充分的中英文业务语义：
   中文描述：说明实体是什么、代表哪个业务对象、承担哪些业务职责、与关键上下游对象的关系及适用边界。应形成完整段落，不能只写“用于记录……”的一句话。

   English Description: Provide an equivalent English business-semantic description with the same scope and level of detail.
4. classAliases 必须提供 4–12 个有用且不重复的中英文别名，覆盖正式名称、常用业务称呼和可靠同义词。不得只把 tableName 或 className 改写大小写充数。
5. entityColumn 使用英文 camelCase，保持一表一类、类内属性名唯一，并优先复用已有本体中的属性名。
6. 每个纳入导出的字段都必须填写 detailedDescription，格式与类描述一致：以“中文描述：”开头，再以“English Description:”提供等价英文。内容应说明字段所表达的业务事实、所属对象、作用范围、与其他业务概念的关系以及资料能够证明的约束；不要描述数据库类型、代码读写、SQL 查询、序列器、接口或程序执行过程。
7. 每个纳入导出的字段都必须提供 2–8 个不重复的 aliases，至少包含自然英文名称和中文业务名称；有可靠资料时补充常用称呼、全称或同义词。别名不能包含未经证实的新业务含义。
8. isLocalId 仅在字段构成本类实例的局部身份键时设为 true；isCode 仅在字段本身表达业务编码时设为 true；isDisplayName 和 isSemantic 也必须依据资料判断。false 不会导出到最终 JSON。
9. 枚举识别不能只看字段名。对于 TYPE、CLASS、STATUS、STATE、MODE、LEVEL、CATEGORY、FLAG、CODE 等候选字段，先搜索已有 entity-classes 中的 enum_ref，再查找对应 enums JSON 或原始备注的明确取值。确认后使用原文件的 enum_name 填写 enumRef，并将可读取的 description、values 和 aliases 准确写入 enumDescription 与 enumValues；最终实体属性只引用 enum_ref，枚举定义单独导出。外键 ID、自由文本和没有有限取值证据的字段不得标成枚举。
10. included 表示字段是否进入 Ontology 和 RDB Mapping。数据类型由 Schema Atlas 根据数据库类型固定转换，无需修改。
11. reason 应简要写明本次命名、标志或枚举判断所依据的文件与业务证据，方便人工审核。
